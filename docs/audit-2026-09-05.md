# Enforcement audit — September 5, 2026

## Decision

The bundle should run as a two-layer system. A short global host rule consults `development-skill-router` for every task. The router then loads only the two to five capabilities needed for the current development phase and reports their real invocation names. Installing or loading all 34 registry entries into every prompt would defeat progressive disclosure and increase conflicts.

This audit used the [official Codex AGENTS.md guidance](https://developers.openai.com/codex/guides/agents-md), [official Codex skill guidance](https://developers.openai.com/codex/skills), the [official Google Antigravity rules codelab](https://codelabs.developers.google.com/getting-started-agy-ide), the [official Google Antigravity skills codelab](https://codelabs.developers.google.com/getting-started-with-antigravity-skills), and the [Agent Skills specification](https://agentskills.io/specification).

## Urgent findings

| Finding before 0.2.0 | Impact | Resolution |
|---|---|---|
| A globally installed skill was still selected on demand. No global rule required it. | The router could be skipped entirely, so “every task” was not enforceable. | The installer now maintains a bounded rule in Codex's active global `AGENTS.md` and Antigravity's `~/.gemini/GEMINI.md`. It preserves all text outside its markers. |
| The installer copied only the router. On this machine, only 4 of 26 primary executable invocation names existed in Codex and 5 of 26 in Antigravity. | Most reported capabilities could not actually run. | A normal global install now downloads all 26 primary upstream skills and 22 transitive Expo skills from their reviewed commits. `--router-only` remains available as an explicit smaller installation. |
| Eleven registry IDs differ from upstream `name` values. | Reports such as `flutter-architecture` did not identify the skill hosts can invoke (`flutter-apply-architecture-best-practices`). | `registry/invocations.json` records and validates actual frontmatter names. Human reports use those names. |

## Major findings

| Finding before 0.2.0 | Impact | Resolution |
|---|---|---|
| The collision guard also rejected every legitimate router upgrade. | A correct 0.1.0 global installation could not be updated. | New installations include file hashes and permit upgrades only when managed files are unchanged. A reviewed legacy installation can be adopted once with `--adopt-legacy`. |
| Flutter routing claimed to require a target but accepted none. | A mobile or desktop platform pass could use the wrong conventions. | Flutter now fails closed until `ios`, `android`, `windows`, or `macos` is explicit and compatible. |
| API routes selected `api-design` without returning `references/api.md`. | The named guidance was not loaded. | API task and API scope routes now return the API reference. |
| `expo-ui` was registered for design but never selected, and mobile review omitted its target UX reviewer. | Useful registered guidance was unreachable through normal routing. | Expo design selects `expo-native-ui`; mobile reviews select the iOS or Android reviewer when a target is supplied. |
| The output had only machine-oriented JSON. | Agents could silently route without giving the user the requested bundle report. | `cli.mjs report` emits a first-line bundle disclosure, route, references, and selection reasons. The global rule requires the same disclosure at task start, phase changes, and final completion. |
| Expo's upstream router delegates to 22 sibling skills, and its `version` frontmatter is rejected by Codex's current validator. | Expo tasks could select missing follow-on instructions, while two installed entrypoints could fail discovery. | The installer includes the complete pinned Expo family. It preserves the upstream version in `BUNDLE_SOURCE.json` and removes only the unsupported frontmatter key from installed copies. |
| Capability manifests named a reviewed commit but did not record file hashes. | Accidental local edits could still be reported as pinned. | Version 0.3.0 records an exact SHA-256 file inventory. The installer and doctor reject missing, changed, or added files. |
| The doctor checked only that a router file and global-rule markers existed, and emitted two concatenated JSON objects for `--target all`. | A stale or modified router or rule could appear healthy, and multi-host output was not valid JSON. | The doctor now verifies the router version and hashes, requires the exact managed block, and emits one JSON array with a host-level `ready` result. |
| Existing same-name skills could only be preserved, leaving 4 Codex and 5 Antigravity capabilities outside the reviewed bundle. | Both hosts had complete-looking inventories that were not fully pinned or structurally consistent. | `--replace-existing` now makes a timestamped backup and installs the pinned copy. `--allow-existing` is an explicit escape hatch that keeps doctor readiness false. |
| Non-development tasks depended on prose alone for the required triage disclosure. | Small wording drift made per-task bundle reports inconsistent. | `node scripts/cli.mjs triage` now returns the exact disclosure deterministically. |

## Minor findings and limits

- Same-name skills are never silently overwritten. Strict mode stops and names the required option; replacement keeps the old directory under the host's `bundle-useful-skills-backups` tree. The September 5 migration preserved 4 Codex and 5 Antigravity originals and left both hosts at 48 of 48 `managed-pinned` capabilities.
- Five framework authorities are live documentation references rather than packaged skills. Current official documentation is appropriate for changing APIs, but a future offline mode would need reviewed snapshots and an update policy.
- WinUI remains `experimental` because that is how its reviewed upstream source presents the workflow. Release work should retain stronger manual verification.
- Host rules are the strongest supported persistence mechanism, but model instruction-following is not a mathematical guarantee. Integration checks must start a new host session because both hosts load global instructions at session startup.
- The installer needs Git and network access for a full inventory install. It fails without silently substituting an unreviewed source.
- This Codex profile already contains a very large skill collection. A new-session behavioral check reported that descriptions were shortened to stay within Codex's initial skill metadata budget. Every skill name remained visible, and the global rule names the router while its report names downstream skills explicitly, but removing unused unrelated skills would improve implicit matching.
- No `agy` command is installed on this machine. Antigravity file discovery, routing, hashes, and global-rule checks are automated; observing model behavior still requires restarting the Antigravity GUI.

## Acceptance criteria

The acceptance checks passed as follows:

- `npm run check`: passed, including 50 doctor, routing, installation, and attribution tests plus registry, licensing, generated-file, and secret checks.
- Full isolated install: 49 skill directories per host (the router, 26 primary upstream skills, and 22 transitive Expo skills).
- Structural validation: all 49 isolated Codex/Antigravity-compatible entries passed.
- Live repeat install: zero changes; all 48 capabilities were already current on both hosts.
- Live doctor: both hosts returned `ready: true`, with 48 `managed-pinned` and zero existing, missing, stale, invalid, unverified, or modified capabilities.
- Live Codex startup test: returned the exact required non-development triage disclosure from the global instruction chain.
- Live Antigravity: files, global rule, router reports, and inventory passed; the `agy` CLI is not installed, so a fresh Antigravity GUI session is still needed for a model-level startup observation.
