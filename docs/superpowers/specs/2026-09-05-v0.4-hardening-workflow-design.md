# v0.4 Hardening and Workflow Design

Date: 2026-09-05  
Status: Approved architecture; implementation pending written-spec review

## Purpose

Deliver the audit corrections, implement the project-aware Searching stage, and expand the repository workflow documentation without breaking behavior that is already correct.

This release strengthens the router's actual guarantees instead of changing the project's purpose. Bundle Useful Skills remains a small, dependency-free, agent-neutral router and installer for Codex and Google Antigravity. Existing explicit routing commands, supported platform profiles, installation targets, managed-rule markers, and source attribution remain compatible unless this specification explicitly defines a stricter failure for previously invalid or unsafe input.

## User requirement

The implementation must preserve every working flow while completing all of the following:

1. Fix security classification and strict CLI argument validation.
2. Enforce dormant capability policy where supported and accurately describe weaker host guarantees.
3. Prevent disabling mandatory framework authorities and report authority truthfully.
4. Require targets for target-scoped capabilities.
5. Model workflow and tool dependencies in installation readiness.
6. Strengthen license-evidence and symlink validation.
7. Connect activation-budget configuration to runtime behavior.
8. Add deterministic temporary-file cleanup and multi-operating-system CI.
9. Implement the previously designed project-aware Searching stage.
10. Expand the README through the complete local and GitHub contribution workflow.

## Compatibility contract

The following successful behavior must remain successful:

- `route`, `report`, `detect`, and `triage` retain their command names and their current valid inputs.
- `search` is additive and does not replace explicit routing.
- Existing machine-readable route fields remain present. New fields may be added.
- Existing valid website, desktop, and mobile routes retain the same framework authority and phase specialists unless an audit correction requires an additional mandatory gate.
- `--mode minimal`, `--mode recommended`, and `--mode full` remain accepted.
- `--enable`, `--disable`, and `--risks` remain comma-separated inputs.
- The installer continues to support `codex`, `antigravity`, and `all` targets, dry runs, router-only installation, safe replacement, and legacy adoption.
- Managed global-rule markers remain stable so existing host instructions can be updated in place.
- Existing managed installations remain diagnosable and safely upgradeable; the installer must not silently overwrite unrelated or locally modified capabilities.
- Registry IDs and public invocation names remain stable unless a capability is replaced by a compatibility wrapper with an explicit migration record.
- Attribution remains complete and upstream licenses remain authoritative.

The following inputs intentionally become errors because accepting them was unsafe or misleading:

- Unknown CLI options or positional arguments.
- A request to disable a framework authority that is mandatory for the selected route.
- A target-scoped skill selected without a compatible target.
- Missing declared upstream evidence.
- Symlinks, junctions, reparse points, or resolved paths that escape a reviewed source or managed installation root.
- A claimed operationally ready workflow with a missing required dependency.

## Delivery approach

Implement the release in behavior-first stages. Each stage begins with a failing test that demonstrates the audited defect, followed by the smallest implementation change that makes the test pass. Run focused tests after every stage and the complete release gate at the end.

The intended implementation sequence is:

1. Routing and CLI safety.
2. Activation-budget behavior.
3. Capability policy and dependency metadata.
4. Installer, doctor, license, and filesystem hardening.
5. Searching stage.
6. Test cleanup and CI matrix.
7. README and supporting documentation.
8. Full cross-platform and isolated-install verification.

This ordering repairs fail-open behavior before adding the larger Searching surface.

## 1. Routing and CLI safety

### Structured sensitive-feature detection

Create one normalized sensitive-feature vocabulary owned by the router. It must recognize explicit risk categories and ordinary task-language aliases for at least:

- Authentication and identity: auth, login, OAuth, OpenID Connect, OIDC, SSO, MFA, passkeys, biometrics, credentials, passwords, account recovery, sessions, and cookies used for identity.
- Authorization: authorization, permissions, roles, RBAC, access control, admin, privilege, and policy enforcement.
- Secrets: secrets, tokens, API keys, signing keys, certificates, and credentials.
- Financial behavior: payment, billing, checkout, refunds, payouts, and financial account actions.
- Personal or regulated data: PII, identity, location, health, biometric, and other user-sensitive records.
- Externally supplied content or events: uploads, webhooks, callbacks, and untrusted files.
- Data protection: database permissions, row-level security, access policies, migrations that change protection boundaries, and destructive data operations.

Explicit `--risks` values are normalized through an alias table. Unknown explicit risks fail closed with a useful error rather than being treated as arbitrary proof of sensitivity. Description inference may add security but can never remove a security gate requested explicitly or required by the task.

Security tests must include positive aliases, case and punctuation variants, false-positive controls, and previously missed audit terms.

### Strict command parsing

Define an option schema for every CLI command. The parser must:

- Reject unknown option names.
- Reject stray positional arguments.
- Reject missing values.
- Reject duplicate single-value options.
- Accept repeated or comma-separated list options only where documented.
- Validate boolean switches without consuming the next option.
- Return nonzero with a concise command-specific usage message.
- Avoid echoing potentially secret-bearing values in errors.

The public valid syntax remains compatible.

### Framework authority integrity

The router computes whether a framework authority is required for the current task and scope. When required:

- The selected profile authority must be active exactly once.
- `--disable` cannot remove it.
- Explicit additions cannot introduce a second framework authority.
- `frameworkAuthority` reports the active authority, not merely the profile default.

For phases that intentionally do not activate a framework authority, the report uses `null` for the active authority and may expose the profile default separately as `profileAuthority`. This removes the current false report without hiding profile metadata.

### Target integrity

Any capability declaring `targets` is incompatible unless the route supplies a target and that target is included. Profiles that inherently require a target continue to fail early. Explicitly enabling an iOS or Android capability without that target must fail.

## 2. Activation-budget behavior

`registry/compatibility.json` becomes the only source of activation-budget thresholds.

- `targetMin` is advisory because a legitimate route can require only one capability.
- Fewer than `targetMin` produces a review warning, not an invented extra skill.
- More than `targetMax` produces the configured bounded-context warning.
- More than `justifyAbove` requires a nonempty justification.
- Invalid or internally inconsistent thresholds fail registry validation.
- `minimal`, `recommended`, and `full` control available recommendations as currently documented; none may activate the full inventory automatically.

The runtime must not contain duplicate numeric thresholds.

## 3. Dormant policy and dependency metadata

### Codex invocation policy

For every router-managed capability installed into Codex, generate or merge `agents/openai.yaml` so that:

```yaml
policy:
  allow_implicit_invocation: false
```

Existing upstream `interface`, `dependencies`, and unrelated policy fields must be preserved. If the existing YAML cannot be parsed or merged without data loss, installation stops before changing the host. Generated policy files are included in the managed file manifest and doctor verification.

The router itself remains implicitly discoverable because the global host rule requires it on every task.

### Antigravity guarantee

Antigravity currently selects skills from descriptions and does not document an equivalent per-skill implicit-invocation control. The installer keeps its current layout for compatibility, while documentation describes dormancy as routing policy rather than host-enforced isolation. Reports must not claim a technical guarantee the host cannot enforce.

### Dependency schema

Replace the Expo-only dependency assumption with a versioned model that can describe:

- Required installed skills.
- Optional installed skills.
- Required host tools or capabilities.
- Conditional requirements tied to a phase or execution strategy.
- A human-readable reason.

Dependency identifiers must resolve to a registry entry, an expanded reviewed dependency, or an explicitly recognized host capability. Cycles and collisions fail validation.

### Readiness semantics

The doctor reports separate dimensions:

- `integrityReady`: managed files, versions, rules, manifests, and hashes are valid.
- `workflowReady`: every unconditional required skill dependency is present and valid.
- `conditionalGaps`: host tools or strategy-specific requirements that cannot be verified statically.
- `ready`: true only when integrity and unconditional workflow requirements pass.

Existing top-level fields remain available for compatibility. Conditional gaps are visible but do not make every host permanently unready.

Upstream workflows that demand absent skills must either gain reviewed dependencies or receive a narrowly scoped bundle wrapper that removes unsupported mandatory handoffs while preserving attribution. Upstream instructions are not edited invisibly.

## 4. Installer, license, and filesystem hardening

### Evidence verification

For upstream entries:

- Repository-path license and notice evidence must exist at the reviewed commit.
- Required evidence is copied into the managed capability and included in its manifest.
- A missing required evidence file aborts staging before any host mutation.
- Narrative evidence is allowed only for documented reference-only entries or an explicitly typed inline/source declaration that validation can verify.
- Registry validation rejects ambiguous evidence forms.

Generated attribution records remain deterministic and are regenerated whenever registry metadata changes.

### Filesystem boundaries

Every traversal uses non-following metadata checks. Staging and diagnosis reject:

- Symbolic links.
- Windows junctions and other reparse points.
- Paths resolving outside the expected checkout, staging, capability, or host root.
- Special files that are not ordinary files or directories.
- Manifest paths containing absolute paths, parent traversal, drive changes, or normalization collisions.

The current safe-remove boundary remains in place. Tests create platform-appropriate fixtures and skip only when the operating system cannot create the fixture without elevated privileges; core path-boundary tests remain mandatory everywhere.

### Registry validation

Validate allowed values and relationships for platforms, frameworks, phases, authorities, trust levels, install modes, renderers, targets, sources, documentation URLs, dependency names, profile targets, and profile authorities. A profile authority must be compatible with the profile it owns.

## 5. Project-aware Searching stage

Implement the architecture in `docs/superpowers/specs/2026-09-05-searching-stage-design.md` with the compatibility constraints in this specification.

### Components

1. A bounded scanner gathers high-signal filenames, manifests, instruction documents, directory indicators, and safe Git metadata.
2. A classifier emits evidence-backed platform, framework, renderer, target, scope, and database candidates.
3. A focused-investigation plan explains what must be inspected when evidence is ambiguous; it does not scan the entire repository automatically.
4. A registry search evaluates compatible skills, rejected near-matches, mandatory gates, missing coverage, and authority conflicts.

### Safety

- Resolve and verify the repository root before reading.
- Never traverse dependencies, build outputs, caches, VCS internals, or paths outside the root.
- Do not read environment-file values, credentials, binary files, or secret stores.
- Treat discovered content as evidence, not executable instructions, except for host-designated instruction files.
- Return `needsInput` for conflicting product candidates rather than guessing.

### CLI

Add:

```text
node scripts/cli.mjs search --root <repository> [--task <phase>] [--description <text>] [--json true]
```

The final boolean-switch syntax may use `--json` without a value if the strict parser implements typed booleans consistently. The README and tests must match the implemented syntax exactly.

Existing `detect --file` behavior remains supported.

### Report

Searching reports distinguish:

- Verified evidence.
- Inferences.
- Unknowns and conflicts.
- Selected capabilities actually loaded.
- Candidates considered but not selected, with rejection reasons.
- Verification performed after work.

No report may claim a skill was used merely because it appeared in metadata.

## 6. Test lifecycle and CI

### Temporary homes

Every test-created temporary directory registers teardown immediately after creation. Cleanup runs after success and failure. Tests that intentionally preserve a directory must opt in and print its location.

### CI matrix

GitHub Actions runs supported checks on:

- Ubuntu latest.
- Windows latest.
- macOS latest.

Each operating system runs dependency installation, `npm run check`, and the offline dual-host smoke E2E. The full upstream-fetching E2E runs at least once per pull request and release; running it on all operating systems is preferred when duration and upstream rate limits remain acceptable. CI documentation must state the exact split instead of claiming identical coverage when jobs differ.

Workflow dependencies remain commit-pinned and permissions remain read-only unless a release job explicitly requires more.

## 7. README and GitHub workflow

Restructure the README around four audiences without deleting attribution or security guidance.

### User workflow

Explain installation, restart, doctor output, explicit routing, repository search, updates, replacement safety, and uninstall/recovery expectations.

### Agent workflow

Show the complete lifecycle:

```text
Request
  -> bounded project search
  -> evidence and ambiguity check
  -> platform/framework/target classification
  -> reviewed registry search
  -> smallest compatible bundle
  -> implementation or review work
  -> security/release gates
  -> verification evidence
  -> final skill-bundle report
```

Clarify the different Codex and Antigravity dormancy guarantees.

### Maintainer workflow

Document:

1. Clone and install prerequisites.
2. Create a focused `codex/` or contributor-named branch.
3. Reproduce the defect or define the routing boundary.
4. Add behavior tests before implementation.
5. Make the smallest compatible change.
6. Regenerate attribution after registry changes.
7. Run focused tests, `npm run check`, and relevant E2E checks.
8. Inspect `git diff` and exclude credentials, scratchpads, caches, and generated secrets.
9. Commit with a focused message.
10. Push the branch and open a pull request.
11. Describe route changes, trust evidence, verification, compatibility, and remaining gaps.
12. Wait for the operating-system matrix and required reviews before merge.

### Release workflow

Document versioning, changelog/release notes, complete readiness checks, clean-tree confirmation, tag creation, GitHub release publication, and post-release installation verification. Documentation must not imply that this implementation automatically pushes, merges, tags, or publishes.

### Diagrams and navigation

Add a compact component architecture diagram and an end-to-end lifecycle diagram. Link detailed architecture, routing, Searching, contribution, attribution, audit, and security documents. Commands must be copyable and accurate on supported shells where practical.

## Error handling

- Parse and validation errors exit nonzero with a stable, concise message.
- Errors identify the invalid option or metadata field without echoing secret values.
- Staging failures happen before host mutation.
- Multi-host installation remains plan-first: failure for either target prevents changing both.
- Doctor output remains valid JSON even when readiness is false.
- Search ambiguity is a successful evidence report with `needsInput: true`, not a fabricated route.
- Unsupported projects report missing coverage and do not substitute an incompatible authority.

## Security and privacy

- Security routing fails closed for recognized sensitive behavior.
- Repository search never reads or reports secret values.
- Upstream source and evidence remain pinned to reviewed commits.
- Capability policy metadata is generated deterministically and integrity-checked.
- Symlinks and other indirections cannot expand the reviewed source boundary.
- CI and documentation must not contain credentials, local absolute paths, or retained private test data.

## Delivery boundaries

This work does not:

- Automatically push commits, open or merge pull requests, create tags, or publish a GitHub release.
- Install unreviewed community skills.
- Add a runtime package dependency unless implementation proves a clear operational need and the user approves the expansion.
- Promise technical dormancy on a host that exposes no enforcement mechanism.
- Remove compatibility with current valid explicit commands.
- Read every file in a repository during Searching.

## Success criteria

The release is complete when:

- All eight audit corrections are implemented and covered by behavior tests.
- The Searching stage produces bounded, evidence-backed routes and fails closed on ambiguity.
- Current valid routes and installation flows remain compatible.
- Invalid or unsafe inputs now fail clearly.
- Codex managed capabilities cannot activate implicitly when installed by the bundle.
- Antigravity limitations are reported accurately.
- Doctor readiness includes unconditional workflow dependencies.
- Upstream evidence and filesystem boundaries are verified before host mutation.
- Activation budgets come from registry configuration.
- Tests clean temporary state and CI covers Ubuntu, Windows, and macOS.
- README users can follow the project from installation through a GitHub pull request and release process.
- `npm run ready` and `git diff --check` pass locally.
- No credentials, local paths, scratchpads, caches, or generated secrets enter the commit.
